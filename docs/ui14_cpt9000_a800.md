### 从已经运行的旧 cache 迁移

旧 cache 和新 cache-prepare 不得同时写同一输出目录。先在旧运行终端按 Ctrl-C，确认旧入口及其 detector 子进程都已退出，再拉取新代码。可以用 `pgrep -af 'prepare_ui14|prepare_ui5_eval_detector|run_ui5_crop_audit'` 核对进程；不要删除缓存目录。新 CPU/GPU 准备协调进程持有 `.ui14-preparation.lock`，同一根目录第二个进程会明确报错，进程退出或被杀后操作系统自动释放锁。旧版本不识别这把锁，因此必须先结束旧进程。

保留当前 repair_v2 数据目录和全部缓存。已完成的 normalize 不必重跑：先在 CPU 节点执行 cache-prepare，成功后再申请 GPU 执行 cache，最后回 CPU 执行 cache-finalize 和 finalize。

扫描的目的仅为建立与现有 detector 相同的图片内容 ID、按内容去重、核对方向后的宽高、生成稳定分片；不读取 GT，也不决定裁剪位置。normalize 的 source_image_id 是解码 RGB 的 SHA256，detector 原有 content_id 是文件字节的 BLAKE2b，直接替换会让旧分片失效，因此本次保留原算法。已去掉外层单独计算 SHA256 统计图片数的扫描，唯一图片数直接使用准备结果。

cache-prepare 默认使用 16 个线程；`UI14_PREPARE_WORKERS=8` 或 `32` 可调整磁盘读取并发。线程池最多保留两倍线程数的待处理任务。按原图路径、文件大小和纳秒级 mtime/ctime 缓存指纹与尺寸，重新运行时仅做多线程 stat 校验；未变的图片不再次读取内容或解码。进度显示 reused/scanned 和当前阶段 ETA。

图片元数据逐条追加到 `cache_preparation/image_info.jsonl`，每累计 32 张新图片或处理循环经过 5 秒时 flush/fsync，结束及异常退出也同步。SIGKILL 可能丢失最后未同步的一小批记录；下次会丢弃未写完的最后一行，保留所有校验通过的完整记录。已有 journal 直接复用；没有 journal 的旧成果只在 CPU 首次建立记录。独立读取尺寸只读图片头及 EXIF，5/6/7/8 交换宽高，不做整图转置；与本批 normalized 尺寸核对。完整 split 的 handoff 与图片属性匹配时不重写 manifest 或分片。单图内容变化时在旧分片槽位更新，未涉及的 GPU 分片保持有效。

每个 split 完成后原子发布 `cache/<task_key>/<split>/manifest/ui14_prepare_ready.json`，绑定 normalization ID、输入 JSONL/manifest、图片清单、分片和 detector 配置的摘要。GPU 入口只检查这些 JSON/JSONL 摘要，不重新 stat/扫描/解码原图；缺少任何一个 split 或摘要失配会在启动首个 GPU worker 前报错，提示运行 cache-prepare，不会自动退回图片扫描。准备后保持原始数据不变，最终 CPU check 仍按原规则复查原图。

原有 detector ID、排序、750 张分片、任务与 split 隔离、检测和裁剪参数均不变，已完成分片继续复用；未完成分片重算。GPU 阶段依次完成全部 split 的 text，再完成全部 icon，中间不执行 CPU 裁剪。GPU 推理本身仍需加载待检测图片。若所有分片已写完但父进程在 stage_summary 落盘前被终止，续跑可直接补齐汇总而不加载 GPU 模型。CPU 收尾继续复用完整的几何计划并生成本批标签。

### GPU detector 每卡 4/5 个进程与已完成分片复用

`UI14_DETECTOR_WORKERS_PER_GPU` 默认 **4**，允许 1–5；设为 5 时四卡最多启动 20 个 detector worker。此参数同时用于 cache 的 PP-OCRv5 text 和 OmniParser icon，二者仍依次执行。它不改变训练阶段 `EVAL_INFERENCE_WORKERS_PER_GPU=2`、四卡训练参数或 `EVAL_FAIL_POLICY=stop`。原 UI5 独立 detector 入口默认仍为 1。

正在运行的进程不会动态增加 worker。先在旧 cache 终端按 Ctrl-C，确认旧协调进程和 detector 子进程均退出，再更新并续跑。仅改变并发不需重新执行 normalize/cache-prepare，也不删除原输出目录：

```bash
cd /mnt/bn/intelligent-service-yg/logging/sicheng_workspace/code/Eagle_LocateUI5_v4/Embodied-ui14-cpt9000
git pull --ff-only origin codex/m32-cpt9000-ui14-v1
UI14_DETECTOR_WORKERS_PER_GPU=4 bash shell/ui14_cpt9000_a800.sh cache
```

需要每卡 5 个进程时，把上面的 `=4` 改为 `=5`。GPU 入口会先核验既有准备清单，然后跳过全部合法已完成分片。协调进程根据本轮未完成分片的快照，先轮流为 GPU 0/1/2/3 分配第一个 worker，再分配各卡第二个 worker，直到每卡配置上限；不启动没有分片可做的 worker。每个子进程通过显式分片名单领取互斥子集，不独立过滤并重新编号会随其他 worker 完成而变化的清单。改变并发或续跑不会改变分片成员、文件名、detector 配置和已完成输出；全部分片完成的 split 不加载模型，已有完整 stage_summary 保持不变。

例如 synth_occlusion/test 的 5,907 张图片按 750 张/片只有 8 个分片。`36b161f` 曾把 worker 按 GPU 分组，导致 8 个分片落在 GPU 0/1，GPU 2/3 空闲；现已修正为四卡各 2 个 worker。每卡 4/5 是并发上限，不是必须启动的空进程数。续跑剩下编号不连续的分片也按本次 pending 清单重新铺开；日志会显示 `pending_shards` 和各卡实际进程数，stage_summary 增加 `active_workers_per_gpu` 和逐 worker 的 `worker_assignments`。少于四个待处理分片或最后收尾时，部分卡仍可能空闲；不为改变并发重切已生成的分片。

只有写出完整 JSONL 和 `.done.json` 的分片可以跳过。旧进程当前正在计算但尚未提交的分片会重算，默认每片最多 750 张；无完成标记的半份 JSONL 不冒充完成。新版在中断、子进程启动失败或任一 worker 失败时停止并回收本轮其他 worker，已完成分片保留。同一个输出根目录仍由一个协调进程持锁管理。

每个多进程 detector worker 使用 2 个图片加载线程，预加载最多 4 张图片，保持输入顺序。队列关闭时释放未消费图片，不再提前解码整个 750 张分片；未显式配置的 OMP/MKL/OpenBLAS 线程数默认为 1，避免多模型把 CPU 线程数放大。图片像素、检测阈值、模型、输出框和 GT-free 几何保持原规则。

日志显示本阶段 `reused`/`pending`，结束时显示 `reused`/`built`。续跑会清理上一轮 worker 进度文件，保留 detector 结果；ETA 不累计旧进程尚未完成的计数。新生成的 `cache/<task>/<split>/detections/{text,icon}/stage_summary.json` 包含 `reused_images`、`new_images`，`throughput_images_per_second` 只计算本次新增图片除以本次检测阶段墙钟时间（包含启动时间）。旧已完成 summary 不改写。

用户日志中的 `synth_occlusion/train text 3000/53047` 是第五个 task/split 的文本检测，约 42 分钟 ETA 只对应该阶段；后面还有其他 split 的 text 和全部剩余 icon。四卡已显示约 69%–75% 利用率，4–5 GB 显存占用不能用来推算线性加速。每卡 4/5 进程的实际峰值显存与新图吞吐由 A800 日志测量，本地 CPU 验证不作为 GPU 性能结果。

### 并行 crop、半成品接续与快速 finalize

若 cache-prepare 已输出 `eval prepare ... 100%`，随后在 `publish_prepared` 报 `File changed during verification: .../manifest/unique_images.jsonl`，说明失败发生在清单摘要与最后 ready 标记的发布阶段。不要删除图片 journal、manifest、分片或 detector/crop 输出。旧报错只说明读取前后 size/mtime/ctime 不一致，未记录具体差值，不能据此判断是属性刷新还是其他进程写入。

此路径现在对单个 SHA256 文件做至多 4 次稳定读取：核对读取前后属性、打开文件与路径的设备/inode、实际读取字节数；仅属性/文件身份变化时等待 0.5/1/2 秒重读该文件。失败尝试的摘要不会被保存；持续变化仍停止，报错包含前后属性以便定位。不会忽略 ctime/mtime 或接受未稳定的摘要。

更新代码后，在 CPU 节点重新执行 `UI14_PREPARE_WORKERS=16 bash shell/ui14_cpt9000_a800.sh cache-prepare`。完整 split 继续 reused；缺 ready 标记但清单/分片已完整的 split，核对当前输入摘要、任务/path/ID/尺寸、样本顺序及全部分片成员，并通过图片 journal 做属性校验，再只补发完成标记，日志显示 `[cache-prepare recovered]`。未变化的图片不会重读或解码，manifest/分片也不改写。缺项或内容失配才进入原有准备流程；持续不稳定的摘要检查直接报错，不因它触发整份清单重建。

`UI14_CROP_WORKERS` 默认 16，可设 8/32；每个 split 按源图 RGB 身份和完整几何计划分组，一个 worker 一次解码生成该图全部 crop，队列最多保留两倍 worker 数。标签按原记录顺序及 tile 顺序输出，重复记录共享 PNG，但保留各自标签、任务与 split。`UI14_PNG_COMPRESS_LEVEL` 默认 1，范围 0–9，`optimize=False`；只影响新 PNG 的压缩，像素、颜色处理与 bbox 不变。编码时计算文件 SHA256，再临时文件写入、fsync、原子替换，不保存后重读。

每个 split 的 `cache/<task>/<split>/crop_index/images.jsonl` 保存逐原图完成记录，绑定原图身份、路径/大小/mtime/ctime、几何计划及 crop 文件摘要。标签单独绑定记录、任务、split、normalization ID。旧完整 split 按标签完成标记中的 PNG 摘要迁移；旧半成品 PNG 首次与预期像素比较后保留原字节并入索引，约 950 张半成品的实际复用量由日志报告。改变压缩级别不重新编码合法旧 PNG。缺失或损坏文件只补对应输出；标注变更只更新相关标签。新几何使用带几何摘要的文件名，旧几何文件保留，避免覆盖其他计划。

每张原图全部 PNG 和标签发布后才追加完成记录；journal 每 32 项/5 秒及退出时同步。被 SIGKILL 时最后尚未同步的 PNG 下次核对后接续，残缺临时文件不算完成。split 全部完成后才发布 `ui14_crop_complete.json`。`finalize` 验证该标记及原图索引，读取 derived/coverage 组装产物；缺失或变化时提示先运行 cache-finalize，不静默进入裁图。

`verification/files.jsonl` 保存实际计算得到的内容摘要/RGB 身份和文件属性；首次内容验证及实际变化项才读取图片，首次验证也使用有界 CPU 线程。`verification/image_evidence.jsonl` 由最终 CPU check 汇总，摘要纳入 CPU 报告。重复 finalize/check、提交和训练启动前验证复用该依据，属性不变时只 stat。任务、split、标签、坐标、来源文件、detector/几何/标签绑定继续验证。`check-full` 绕过历史内容验证缓存并核对 crop 像素，用于独立全量复核。

裁图日志分别显示 `reused`（原图完成索引复用）、`migrated`（旧 PNG 首次接入）、`built`（有新 PNG 写入的原图）和 `pending`。常规完成进度含复用，不能作为新裁图吞吐。专门的 `[crop performance]` 只用 built 原图计算新原图/s 和新 crop/s，每约 10 秒刷新；前 500 张 built 原图直接进入正式缓存，并写 `crop_performance/first_500_built.json`，不中断工作。每次调用的快照另存 `crop_performance/<run_id>/`，最新报告为 `crop_performance/latest.json`。

报告含实际 worker 峰值、读取/解码/编码/写入累计线程耗时、进程 CPU（100% 表示一个核）、RSS/峰值内存、逐 split reused/built/migrated 数量、与旧日志 0.79 原图/s 的比值及约 8 原图/s 的目标。ETA 是按新裁图实测速度估计的 crop 剩余时间；未访问 split 仍可能包含待迁移/复用项，不含 merge、几何和最终组装耗时。尚无新 crop 时不报伪造吞吐或 ETA。低压缩可能增大文件体积，挂载盘是否达到目标只能由远端实测确定。

## 进度、耗时和剩余时间

normalize、cache、finalize 默认每 10 秒刷新一次终端进度，阶段切换时立即输出。显示当前任务/split、已完成数量、百分比、速度、命令总耗时和当前阶段 ETA；扫描图片、源文件摘要、crop PNG/标签生成、原图核验、缓存几何检查和最终产物绑定均有进度。即使当前图片读取、模型加载或 detector 子进程尚未返回，心跳仍显示该阶段已用时间。

## EXIF=0 与 normalize 续跑

normalize 默认按 task/split 续跑，无需增加参数。EXIF Orientation 允许 None/0/1：0 保持现有像素和 bbox，2–8 仍按原规则拒绝，避免原始画布与 detector 画布不一致。这个修正不改变原有共享坐标解析器和 normalization ID；本次已有的成功记录继续兼容。

首次续跑可迁移旧版产物：即使 `normalization_stats.json.complete=false`，只要 source_snapshot 与当前来源/解析器一致，该 split 的 failed_records=0、normalized_records=records=manifest 数量，且 normalized JSONL、detector input JSONL 和 input manifest 的摘要一致，就复用。复用只读现有 JSONL 和文件摘要，不解码、读取或计算原图内容 hash；旧解析差异明细从全局文件按 task/split 迁移。

每个 split 的标注和 detector inputs 写完后，保存 `normalization_splits/{task_key}/{split}.issues.jsonl` 和 `{split}.state.json`。state 包含独立统计、错误、normalization ID 和产物摘要，最后原子写入；未写完的 split 下次重建。旧全局统计与差异明细保留到最终合并，补跑中断后仍可迁移尚未访问的旧成功 split。来源或解析器导致 normalization ID 改变时，不复用旧 ID 的标注。

所有 split 就绪后重新生成任务注册、解析差异合并文件、页面/原图重叠、normalization stats 和 CPU 报告。成功时 complete/normalization_complete 为 true，ready 仍由 finalize/check 决定；全局页面冲突等检查即使全部复用也会重新执行。原图内容的重新校验仍由后续完整 CPU check 执行。

## 实际 CPU 报告字段

normalize 即写 cpu_check_report.json，normalization_complete 表示当前修复批次扫描是否通过；ready 此时为 false。finalize 在完整 cache/recipe/test/checkpoint/YAML 检查通过后才置 ready=true。

- post_repair_sources（normalize 阶段为 tasks）：18 份文件的实际记录数、正负数、失败数、来源 bbox 配置、所选 GT 字段与坐标依据。
- formats：真实格式的记录数及出现次数。numbered_rect_err_with_rectN_records、two_point_box_records、objects_single_object_records、location_direct_coordinates_records、location_bbox_wrapper_records 对应此次审查样例。
- parser_comparison.legacy_parse_failure_records：旧主图/框/JSON 解析失败的记录数；legacy_consumer_failure_records 还计入旧 split 拒绝、缺少标注字段和重复记录 ID。各原因可重叠，总失败数按记录去重。
- parser_comparison.parse_result_difference_records：两边均解析成功后，主图或有序多框列表不同的记录数（坐标比较容差 1e-7 像素）；失败不混入差异数，差异也不直接等同于真实错误标签。逐条来源与结果写 parser_compatibility_issues.jsonl。
- repair_run_id/source_files/repair_summary：修复批次、20 份源文件摘要及裁框/隔离/移动统计。ui9_page_split 和 image_overlap 分别记录页面、原图级归属。

真实提交和每段启动均重新校验源文件与产物摘要；源批次、解析器或缓存标签索引改变后，旧 ready 报告不能用于运行。此检查只约束数据一致性，不引入训练实验、smoke 或新的指标早停策略。
