## 任务与标注约定

统一注册表实现在 `eaglevl/ui_task_registry.py`。原 UI5 模型 ID 为 0 overflow、1 cropping、2 occlusion、3 ellipsis、4 missing；训练别名和旧评分 class_id 映射保持兼容。

| ID | task_key | view_policy | relation_family |
|---:|---|---|---|
| 0 | text_overflow | crops | boundary |
| 1 | cropping | crops | boundary |
| 2 | occlusion | crops | pairwise |
| 3 | text_ellipsis | crops | text |
| 4 | content_missing | full_image | presence |
| 5 | ui_alignment | full_image | pairwise |
| 6 | change_line_illegal_v3 | crops | text |
| 7 | synth_cropping | crops | boundary |
| 8 | synth_occlusion | crops | pairwise |
| 9 | synth_radius | crops | boundary |
| 10 | synth_loneword | crops | text |
| 11 | synth_large_margin | full_image | pairwise |
| 12 | synth_inner_margin | crops | boundary |
| 13 | synth_small_margin | crops | pairwise |

两个已有来源按 manifest 的 bbox 配置和 `objects.bbox/bbox_type` 转换。合成来源使用 ScreenShotURL 和 Objects.Location；Objects 支持单对象/对象列表，Location 支持 JSON 字符串、直接坐标、bbox 包装和 rect 字段字典。两点 `[[x1,y1],[x2,y2]]` 是一个矩形。

GT 优先级严格使用 v2.1：`rect_err(?:_?数字)? > rect_mbr(?:_?数字)? > rect数字*_shift > rect_combine(?:_?数字)? > rect数字*`，匹配不区分大小写，同级按准备脚本的键排序保留多框，包括 rect_err_1。原图标注已 repair 裁框；接入只投影一次，不再次裁框或把无效框变成负样本。

合成框先用 `s=W/375` 将 X/Y 四个坐标同时转换为原图像素，再减 crop 偏移，最后按当前输入宽高转 0–1000。`BBoxCanvasWidth` 声明非 375 会报错。正常框使用原有四舍五入；裁剪产生的小于一个归一化单位的片段向外量化一个单位，避免静默丢框。每个来源保存 source_dataset/source_version/source_record_id/source_image_id/split/task_key/crop_id。

训练问题全部由注册表生成 `Locate all the instances that match the following description: ...`，答案使用原 `<ref>...<box>...` / `<box>none</box>` 格式。原 messages 仅在原始来源资料中保存。正样本必须选择 ScreenShotURL；现有记录明确 `Objects=[]` 且没有 ScreenShotURL 时，仅允许 LocalImgURL 作为该条负样本输入，不以 RawImgURL 或 images 猜测主图；从不因参考图存在而生成新负样本。

UI5 保留审核 marker、排除清单及全部有效人工修复记录。修复目录中的新缓存沿用 PP-OCRv5 / OmniParser 的 detector 配置，OCR Python 从旧缓存 `detections/text/stage_summary.json` 读取，默认后备为 `conda_envs/UI5PaddleOCR/bin/python`；可用 `--text-python` 显式指定实际环境。

新七项仍使用 v5 原始 detector 边缘、严格横向分区和相同 DP。额外的 `ui14_detector_neighbors_v1` 只排除会拆开相近且横向重叠的 detector 关联组的候选线：文本保留相邻行，boundary/pairwise 保留邻近容器/元素。没有合适的原始边缘时按 v5 减少 crop 数至单张全宽 scan。该规则只读 detector，不读 GT；覆盖报告不会触发 GT repair、过滤测试数据或重排测试 crop。

## 正式训练、恢复与评测

初始化固定为 `${WORKSPACE}/gui_models/locany-3b-ui-cpt-v4-v3-h20x2-formal-segmented-eval/checkpoint-9000`。
BASE_MODEL=MODEL_PATH=INIT_CHECKPOINT，INIT_CPT_STEP=9000，LOCANY_CPT_MODE=0。新 SFT 从 optimizer step 0 开始，CPT 的 optimizer/scheduler 不恢复；恢复只使用新运行目录内的 SFT checkpoint。

输出：`${WORKSPACE}/gui_models/locany-m32-cpt9000-ui14-a800x4-repair-v2`。使用独立输出目录避免恢复修复前数据的 optimizer；ui14_training_data.json 绑定 repair 批次，后续分段只能恢复同一批次。
运行 profile 为 `configs/ui14_cpt9000_formal.json`：单节点 A800 40GB × 4，group_id=2146，`ies_aiai_experience/AIAI_locate`，队列 `compute-3302-yg-cloudnative-ai-aiai.locate-guarantee`；SDPA、BF16、ZeRO-2 two-lr、batch=1、GA=2、sequence/sample=7268、每 rank tokens=12800、16k optimizer steps、seed=42、warmup=500、cosine、LR=1e-5/relation LR=2e-5、weight_decay=.01、grad_norm=1。MoonViT attention、M32、PBD、observe gate 和其余损失沿用基线。

14 路默认采样权重各为 1。每路按源图均衡并轮换 crop；双侧任务 negative:positive=2:1，单侧任务只抽取实际存在侧，并记录实际比例。task-indexed embedding、expert、image gate 和输出头扩展至 14；relation family 保留 4。checkpoint config 和 processor 保存任务数量与完整注册表，patch 同步导出可独立加载的注册表模块。

每 100 optimizer steps 写训练窗口。底层保留每步 scalar 收集，以计算 100 步窗口；不是每 100 个 microbatch。
每 1000 SFT optimizer steps 分段退出训练，四张卡各一条独立评测 worker，完成任务继续领取，完整跑同一 checkpoint 的 14 项 test。评测只读预生成缓存。新九项不做 Figma 路径/文件名过滤；旧五项 no_figma 和 1555 原图口径保持原值。预测先映回原图合并，随后使用原 IoU=.1、Hungarian 匹配和非法输出惩罚。

评测结束恢复 optimizer、scheduler、RNG、数据进度，总 MAX_STEPS 仍是 16000，学习率不按分段重新 warmup。固定 `EVAL_FAIL_POLICY=stop`：评测执行失败立即停止后续训练，保持当前 checkpoint，修复后执行同一提交命令补齐本轮，再继续训练；不以缺失 UI9 的 UI5 结果判定完成。

`${OUTPUT_DIR}/diagnostics/ui5_training_evaluation.xlsx` 保持两个 sheet：

- `train_100steps`：新增九项独立 loss、样本数、正负、gate、M32 诊断及任务来源/初始化信息。
- `eval_1000steps`：每轮 36 行，14 项 × image/bbox，加 five_task_macro/micro 和 ui9_macro/micro 各 image/bbox。bbox TN 留空；无负样本来源 negative_count=0。

每 4k 正式 checkpoint，以及每 1k 严格提升的旧 UI5 image/bbox macro F1 最佳 checkpoint，保留策略沿用基线。UI9 单独展示，不参与旧 best 字段。逐图预测、gate sidecar、evaluation_history、best_checkpoints 和 ui14-step 完整性状态均保留。

## 实际 CPU 报告字段

normalize 即写 cpu_check_report.json，normalization_complete 表示当前修复批次扫描是否通过；ready 此时为 false。finalize 在完整 cache/recipe/test/checkpoint/YAML 检查通过后才置 ready=true。

- post_repair_sources（normalize 阶段为 tasks）：18 份文件的实际记录数、正负数、失败数、来源 bbox 配置、所选 GT 字段与坐标依据。
- formats：真实格式的记录数及出现次数。numbered_rect_err_with_rectN_records、two_point_box_records、objects_single_object_records、location_direct_coordinates_records、location_bbox_wrapper_records 对应此次审查样例。
- parser_comparison.legacy_parse_failure_records：旧主图/框/JSON 解析失败的记录数；legacy_consumer_failure_records 还计入旧 split 拒绝、缺少标注字段和重复记录 ID。各原因可重叠，总失败数按记录去重。
- parser_comparison.parse_result_difference_records：两边均解析成功后，主图或有序多框列表不同的记录数（坐标比较容差 1e-7 像素）；失败不混入差异数，差异也不直接等同于真实错误标签。逐条来源与结果写 parser_compatibility_issues.jsonl。
- repair_run_id/source_files/repair_summary：修复批次、20 份源文件摘要及裁框/隔离/移动统计。ui9_page_split 和 image_overlap 分别记录页面、原图级归属。

真实提交和每段启动均重新校验源文件与产物摘要；源批次、解析器或缓存标签索引改变后，旧 ready 报告不能用于运行。此检查只约束数据一致性，不引入训练实验、smoke 或新的指标早停策略。
